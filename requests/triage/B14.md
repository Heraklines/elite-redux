## Disagreements with LIBRARY-DECISIONS.md

- **D1 `field.slot-charged` (section 5, "private WeakMap or module field").** The decision (Rejected) is right, but the reason is not: the
  mark is a public positional tag (RAI:150-157, 163-165). It should be rejected because it has one writer (Electrodynamics) and its reader
  rewrites module memory and the tag list through `resetBattleLocalState` (RAI:81-95).
- **D2 charge stacks lumped into the private-memory rejection** ("... B13-50, B14, B15 ..."). The rejected `mon.has-stored-charge`,
  `time.charges` and `effect.store-charge` were B13's Porous counter (B13.md:81-99). B14's `charge-stack.ts` is a different store: it
  is exported, shared by three abilities and six attrs, and read by `field/pokemon.ts` (:67, :8724) and MoveEffectPhase. A player can
  name it ("charge stacks"). R-B14-6.1 and 6.2 are Justified-unbuilt, not Rejected.
- **D3 `effect.add-type` (section 4, Planned for "B08-4, B08-46").** The registry entry follows B08-4: `requires: ["other"]`, a `target`,
  and the feasibility "nothing to a Terastallized Pokemon" (`summonData.addedType`) (V/effects-library.ts:339-348). B08-46 and
  Photovoltaic use another formula: append to `summonData.types`, dedupe, no Tera check, no `updateInfo` (FPM:350-353), on
  `event.on-entry`, which provides no `other` (V/when-registry.ts:98). As registered, the effect cannot compile for either of these users.
  It needs a mode setting (or two ids), and `requires` must depend on the target.
- **D4 `effect.set-matchup` covers Miracle Blade.** B14 called it "the same request as Bone Zone", and LIB planned one effect for B08-11
  and B12-41. The planned entry ("make an immune matchup count as a normal hit", one number) cannot express Miracle Blade's per-type
  division rule (FPM:2029-2047), so for B14 it is a package (C2-i).
- **D5 `party.ally-active` (section 1, "asked by B03, B13-29").** B14-5.8 asked for "any active ally"
  (`getAllies().find(isActive)`). The built atom reads only the first ally (`getAlly()?.isActive(true)`). They agree in singles and
  doubles but not in triples, so B14-5.8 is not answered by it.
- **D6 `move.ability-can-change-type` (section 1, "MoveTypeChange (13 legacy users), ElectrodynamicsGalvanize ... can use it now").**
  The atom is only clause 1 of `anyTypeMoveConversionCondition`. The rest (Tera Blast, and Tera Starstorm when Stellar Terapagos)
  needs `mon.tera-type` and `mon.species`, which were not built (init-abilities.ts:2380-2401; RAI:111-129). The legacy closures of those
  15 attrs cannot be fully rebound yet.
- **D7 alias `effect.lose-hp-percent` → `effect.hurt-percent-of-max-hp`.** The B02-2 formula also does
  `attacker.turnData.damageTaken += chip` (B02.md:49-50). Overloaded's chip does not (ELV:345-346). Either the planned effect gets a
  setting for that write, or the alias is wrong for R-B14-7.1.
- **D8 `not-simulated` was never decided.** B02 (B02.md:107), B14 (chunks 1, 2, 3, 6, 7) and B18 (R-B18-1) ask for it. LIB has no line
  on it. Decision here: a guard for the classes that test `simulated` in `canApply` (C1-c), and no guard where the test is in `apply`
  (C6-a, C7-b).
- **D9 `effect.set-marker` rejected as private memory.** `erAbilityProvenance` is the shared marker memory that LIB itself reads with
  `time.marker-set` (section 1). A plain `push(key)` write (no timer, unlike B17 R9's tick) is the missing other half for Celestial
  Jelly, Booby Trap, Eulogy, Oracle entry, Ballaster and Somniloquy (writers FPM:328, 859, 892, 1465, 2154, 2357). The rejection
  reason does not apply to this form.
- **D10 `effect.survive-lethal-hit`** exists as a base planned entry with no settings (V/effects.ts:179-189). LIB never mentions it.
  Celestial Jelly's damage rewrite with an HP share is not Sturdy's tag mechanism, so it needs the `hpFraction` setting and the bundled
  knockout guard (3.5, 3.6).
- **D11 coverage claims.** Section 8 says no unnumbered or table entry of B14 was built, and section 9's index omits B14. In fact MC built
  2.1, 2.3, 3.1, 4.1, 4.3, 4.8, 4.9, 5.1 and 6.11 (V/when-registry.ts:112, 664-698, 1132-1143). The two chunk 1 markers (C1-k) were
  missed.
- **D12 guard `hit-dealt-damage` (section 2, "asked by B14").** The B14 request was the pair `damage > 0 && hitResult < NO_EFFECT`. The
  built guard is only `damage > 0`, so B14's ask is answered by the two guards `[hit-dealt-damage, hit-connected]` in order, not by
  this one alone.
