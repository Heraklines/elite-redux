## Disagreements with LIBRARY-DECISIONS.md

1. **R3 / Lingering Musk**: section 1 line 65 lists LingeringMuskPostTurn as a user of `time.marker-set`. Its marker is
   the loose field `tempSummonData.lingeringMuskFaint` (bernerd:393 writes, :408 reads), and `time.marker-set` reads only
   `erAbilityProvenance` of battle/switch-in/turn data (evaluate/conditions.ts:731-734). Rebinding it would always answer
   false. It needs the marker moved into provenance memory first (owner decision noted in R3).
2. **R9 / R15 rationale**: section 5 line 135 rejects `effect.set-marker` as "memory that lives in a private WeakMap or
   module field". The B17 markers live in `erAbilityProvenance` on `battleData`/`summonData`/`turnData`, the same engine
   memory LIB already exposes for reading through `time.marker-set`. The write half is generic (four writers above), so
   it is Justified-unbuilt; only `tick-marker` (Oracle's countdown suffix) is a one-off.
3. **R2, R19** are not named in LIBRARY-DECISIONS but already exist in the registry as Planned (`effect.survive-lethal-hit`,
   `effect.change-form`).
4. **R12**: LIB section 5 line 123 aliases `hit.landed` correctly, but section 5 line 136 also sweeps R9 to R16 into
   "one-off" Rejected; R11 (Planned, section 4) and R12 (Alias) are exceptions to that range.
5. **R21**: LIB plans `effect.reset-stat-stages` for B03 (line 116) but its only param is `target` with the holder /
   other / sides options. R21's "only raised stages" rule is not expressible, so rebinding
   `ClearOpponentStatBuffsOnSummonAbAttr` to the planned effect would also wipe lowered stages.
6. **R34**: the planned `effect.hit-n-times` reads as "set the hit count" (param `count`, default 2). Every
   `HitMultiplierAbAttr` user adds (`+=`), so wiring the planned effect as written would change behaviour.
7. **R23 to R39** (chunks 3 and 4) are not named anywhere in LIBRARY-DECISIONS except R24 and R26 (section 1);
   section 9 claims every unnamed id is covered by section 5's cluster rules, but R28 (composition alias), R30, R33,
   R34, R35, R39 are multi-user and fall under no rejection rule.
